# Ревью `BookingController`

Проверено чтением кода и вживую в Docker: запросами к API, `tinker` и трассировкой фреймворка (`vendor/`). Ссылки на строки — `app/Http/Controllers/BookingController.php`, если не указано иное.

## Critical

### 1. SQL-инъекция в `store` (строки 23–26)

`room_id`, `starts_at`, `ends_at` интерполируются в SQL без плейсхолдеров:

```php
DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'")
```

Пример: `"ends_at": "11:00'; DROP TABLE bookings; --"` — произвольный SQL от имени пользователя БД. Отдельно: нечисловой `room_id` или `null` даёт синтаксическую ошибку SQL → 500.

**Исправление:** параметризованный запрос (`DB::select(..., [$a, $b, $c])`) или конструктор запросов Eloquent/Query Builder. Правильная валидация входа (см. п. 4) отсекает мусор до SQL.

### 2. Mass assignment и подмена автора в `store` (строка 37)

`Booking::create($request->all())` при `user_id` в `$fillable` (`app/Models/Booking.php:11`): клиент бронирует от имени другого пользователя. Отсутствие `user_id` — отдельная 500-ошибка (FK/NOT NULL в БД) вместо 422. Через `$request->all()` в модель попадают и любые лишние ключи.

**Исправление:** FormRequest c whitelist-правилами, автор — только из токена: `Booking::create([...$validated, 'user_id' => $request->user()->id])`.

### 3. Отменить бронь может кто угодно — `destroy` (строки 45–50)

Проверки автора нет. Проверено вживую: токеном Бориса удаляется бронь Анны — `204 No Content`.

**Исправление:** `abort_unless($booking->user_id === $request->user()->id, 403)` или Policy (`$booking->user()->is($request->user())`), плюс route model binding `Booking $booking`.

## Major

### 4. Валидации нет вообще — мусорный вход даёт 500 вместо 422 (строки 21–37)

- `starts_at`/`ends_at` не проверяются: некорректная дата → исключение `Carbon::parse` → 500; несуществующий `room_id` → FK-ошибка БД; нет проверки `title`.
- Правила ТЗ не реализованы: длительность 15 мин – 4 ч; шаг 15 минут; конец брони не проверяется.

**Исправление:** `StoreBookingRequest`: `room_id` → `exists:rooms,id`, `title` → `string`, даты → `date` + `after:starts_at` + собственное правило длительности/шага. Все ошибки — стандартный 422 Laravel.

### 5. Смещения времени теряются при записи — «кто в какой таймзоне прислал»

Колонки `timestamp` без tz + каст `datetime`: строка `2026-11-06T10:00:00+03:00` сохраняется как `2026-11-06 10:00:00` (стенное время, смещение выброшено). Проверено вживую: отправил `10:00+03:00`, в БД лежит `10:00:00`, а API отвечает `2026-11-06T10:00:00.000000Z` — уже как UTC. Следствие для одной комнаты: `10:00+03:00` и `14:00+07:00` — один и тот же момент, но сохраняются по-разному и пересечение не детектируется (и наоборот, ложные конфликты).

**Исправление:** единая точка отсчёта. Парсить даты в Carbon, приводить к UTC **до** сравнения и записи; при выводе тоже UTC (или локальное время офиса с указанием смещения). Надёжнее — колонки `timestamp(0) with time zone` (`timestamptz`).

### 6. Проверка рабочего времени неверна (строки 32–35)

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20)
```

Три ошибки:
- `Carbon::parse` сохраняет смещение клиента (проверено: для `+03:00` → `hour` = 10). Проверяется время клиента, а не офиса комнаты: бронь `10:00+07:00` для московской комнаты — это 08:00 по Москве, рабочее время не выполняется, но пройдёт проверку.
- Проверяется только начало: бронь 19:30–23:00 допустима.
- Требование «бронь целиком в 09:00–20:00» не выполняется и для валидного конца в 20:00 (минуты игнорируются: `hour` = 19 у 19:59).

**Исправление:** перевести `starts_at` в tz офиса комнаты (`Carbon::parse(...)->timezone($room->office->timezone)`), проверить весь интервал: `starts_at >= 09:00` и `ends_at <= 20:00` того же дня.

### 7. Пересечение запрещает встречи «впритык» (строки 23–26)

`starts_at <= '{$ends_at}' AND ends_at >= '{$starts_at}'` — нестрогие сравнения. По ТЗ «впритык» разрешено: для `10:00–11:00` и `11:00–12:00` условие даёт ложный конфликт (11:00 <= 12:00 и 11:00 >= 11:00).

**Исправление:** строгие сравнения: `starts_at < newEnd AND ends_at > newStart`.

### 8. `today()` считает «сегодня» в UTC, а не в tz офиса (строки 52–61)

`today()` — полночь в `app.timezone` = UTC. Для Новосибирска (UTC+7) после 17:00 МСК «сегодня» уже завтра; плюс в БД лежат стенные времена в разных смещениях (п. 5) — сравнение дат ненадёжно.

**Исправление:** границы дня считать в tz офиса: `[$dayStart, $dayEnd] = [now($tz)->startOfDay(), now($tz)->endOfDay()]` в UTC и `whereBetween('starts_at', ...)`.

### 9. Гонка: двойная бронь одного слота (бонусное задание, строки 23–37)

Проверка конфликта и `create` — не атомарны (check-then-act). Два одновременных запроса проходят проверку → две брони на слот.

**Исправление:** (а) транзакция + `SELECT ... FOR UPDATE` на строку комнаты (или advisory lock по `room_id`) вокруг проверки; (б) надёжнее — exclusion-ограничение PostgreSQL: `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`, конфликт ловится на insert; (в) на уровне приложения — сериализуемые транзакции. Вдобавок запросу конфликта нужен индекс `(room_id, starts_at)` — сейчас полное сканирование таблицы. Опишу выбранный вариант в README.

## Minor

### 10. N+1 в `today()` (строка 59)

`$b->user->name` — запрос на каждую бронь. **Исправление:** `->with('user')` / `load('user')`.

### 11. `store` отвечает 200 вместо 201 (строка 42)

Семантика REST: создание ресурса — `201 Created`. **Исправление:** `response()->json($booking, 201)` или `return response()->created(...)`.

### 12. `booking_id` не попадает в `bookings.log` (строки 39–40)

`Log::withContext()` у фасада проксируется на **дефолтный** канал (`LogManager::__call` → `driver()->withContext()`), а сообщение пишется в канал `bookings` — контекст туда не доходит. Проверено вживую: в логе строка `Booking created` без `booking_id`, аудио-лог цели не выполняет. Дополнительно контекст остаётся в дефолтном канале до конца запроса (для Octane/queue — дольше).

**Исправление:** `Log::channel('bookings')->info('Booking created', ['booking_id' => $booking->id])` — контекст прямо в вызове, без `withContext`.

### 13. Методы контроллера без типов (весь файл)

`index`/`store`/`today` без return-типов, `destroy($id)` — без типа параметра. Против правил проекта (PHP 8.4, явные типы обязательны) и отличается от остального кода (модели/миграции типизированы).

**Исправление:** при переписывании методов проставить типы: `public function store(StoreBookingRequest $request): JsonResponse`, `destroy(int $id)` и т.п.

### 14. Без `Accept: application/json` неаутентифицированный запрос даёт 500 вместо 401

Задокументировано в README как известная особенность; механизм такой. `Authenticate::unauthenticated` (`vendor/.../Auth/Middleware/Authenticate.php:87`):

```php
$request->expectsJson() ? null : $this->redirectTo($request)
```

Без заголовка `Accept` вызывается редирект-колбэк, который по умолчанию ставит `ApplicationBuilder::withMiddleware` (`redirectGuestsTo(fn () => route('login'))`). Маршрута `login` в API-приложении нет → `RouteNotFoundException` → 500. Проверено трассировкой вживую.

**Исправление:** в `bootstrap/app.php`: `$middleware->redirectGuestsTo(fn () => null)` — тогда исключение дойдёт до хендлера, а `shouldRenderJsonWhen` (уже настроен на `api/*`) вернёт 401 JSON.

### 15. `today()` отдаёт время без контекста таймзоны (строка 58)

`$b->starts_at . ' – ' . $b->ends_at` — стенное время «как лежит в БД» (см. п. 5), потребитель не знает, в каком оно поясе. **Исправление:** форматировать в tz офиса, смещение указывать явно.

## Не проблемы (выглядит подозрительно, но ок)

- **`orderByRaw('starts_at DESC')` в `index` (строка 17)** — строка статическая, инъекции нет. Стилистически чище `->latest('starts_at')`, но это не дефект.
- **409 на конфликт вместо 422** — корректный REST-статус для конфликта ресурсов; 422 в ТЗ требуется для ошибок валидации, они и будут 422.
- **`findOrFail` → 404 в `destroy`** — ожидаемое поведение для отсутствующей брони.
- **`paginate(20)` в `index`** — разумное значение по умолчанию.
- **`timestamp` без tz в миграции** — не дефект сам по себе, но требует единого соглашения «везде UTC» (п. 5); `timestamptz` снял бы класс ошибок с хранением.

## Приоритет исправления

1. П. 1–3 (инъекция, mass assignment, права на удаление) — безопасность.
2. П. 4–8 (валидация + время/пересечения) — требования ТЗ, одно общее решение: FormRequest + нормализация в UTC + tz офиса для рабочего времени.
3. П. 9 — гонка (бонус).
4. П. 10–15 — мелочи, по ходу.
